## Вывод

Три конкретных замечания компании исправлены: появился отдельный слой репозиториев/UoW, домен отделен от ORM, обработка находится в application, а не в messaging. Повторный аудит не обнаружил возвращения этих нарушений.

## Обоснованные замечания

### R1. P2 — ошибка программирования расходует бюджет доставки и теряет подробности

**Где:** [application/processing.py](app/application/processing.py), строки 58–60 и 74–77; обработчики в [worker.py](app/worker.py), строки 108–112 и 167–168. Связанная проблема — [main.py](app/main.py), строки 70–74.

**Как сейчас:** любой `Exception` при вызове шлюза или webhook трактуется как ошибка очередной попытки. Для большинства исключений сохраняется только имя класса. Ошибка в коде адаптера, например `TypeError`, обрабатывается тем же путем, что и временная недоступность внешнего сервиса. В API все `SQLAlchemyError` и `OSError` превращаются в сообщение о временной недоступности БД, хотя не каждое такое исключение означает отказ соединения.

**Что воспроизведено:** подставной шлюз выбрасывает `TypeError("injected_programming_error")`. После трех вызовов processor платеж исчерпан, сформировано событие DLQ, `last_error=TypeError`. Ни одна запись прикладного логгера не содержит `exc_info` со стеком исключения. Это намеренно внедренная ошибка в проверке, а не обнаруженный сбой работающего эмулятора.

**Почему придерутся:** очереди выглядят работающими, но регрессия адаптера будет расходовать попытки платежей и скрывать место поломки. Оператор увидит название исключения без причины и строки кода. Ответ `503` на программную ошибку БД также направит диагностику по неверному пути.

**Как исправить:** определить ожидаемые ошибки портов шлюза и webhook; преобразовывать сетевые/HTTP-ошибки в них внутри адаптеров. Расходовать логические попытки по явно выбранной политике. Неожиданные ошибки отдельно регистрировать со стеком и идентификаторами и передавать на уровень управления worker. Для неожиданной системной ошибки предусмотреть контролируемую паузу/сигнализацию, чтобы простая смена `except` не создала бесконечный быстрый цикл переподключений. В ответ `503` переводить ожидаемые инфраструктурные сбои, а не любые ошибки ORM. При логировании исключений исключить секреты, полные URL и параметры запросов.

**Критерий закрытия:** временная ошибка дает предусмотренный retry; `TypeError` диагностируется со стеком и не маскируется под обычный отказ доставки; ошибки соединения и программные ошибки БД различаются.

### R2. P2 — домен существует, но не защищает все свои инварианты

**Где:** [domain/payment.py](app/domain/payment.py), строки 30–55 и 83–90; [application/commands.py](app/application/commands.py), строки 8–15; [application/payments.py](app/application/payments.py), строки 15–29 и 37–51. Денежная валидация находится в [schemas.py](app/schemas.py), строка 19.

**Как сейчас:** HTTP-схема запрещает отрицательные суммы и лишние дробные знаки. Но `Payment` и `CreatePayment` — dataclass без проверки этих ограничений; прикладной сервис не проверяет их повторно через домен. Аннотация `Decimal` сама по себе не валидирует значение. `RetryPolicy` также допускает отрицательную задержку при прямом создании.

**Что воспроизведено:** `Payment` принимает `Decimal("-1.00")` и `Decimal("1.001")`. Прямой вызов `PaymentService.create(CreatePayment(amount=Decimal("1.001"), ...))` на настоящем PostgreSQL успешно сохраняет `1.00`. Дополнительная проверка `current_attempt=4` с последующим `record_failure` возвращает попытку 5; `RetryPolicy(-5)` дает отрицательную задержку. Эти состояния передаются напрямую из Python, обходя HTTP.

**Граница вывода:** текущий HTTP API сумму `1.001` отклоняет. Ошибка не доказывает, что обычный внешний запрос сегодня может незаметно округлить деньги. Она доказывает зависимость корректности прикладного сценария от единственного входного адаптера.

**Почему придерутся:** для команды, отдельно потребовавшей доменный слой, естественен вопрос «где гарантируется корректность сущности, если завтра появится CLI или другой consumer?». Сейчас бизнес-ограничения частично остаются в Pydantic и БД.

**Как исправить:** сделать проверяемую доменную фабрику или простой тип денежной суммы; проверять положительность, конечность, точность и вместимость до вычисления fingerprint и до репозитория. Не округлять вход молча. Проверять диапазон попыток и параметр retry. Восстановление сущности из БД должно иметь понятный контракт допустимых состояний. Для этого не нужна тяжелая иерархия классов.

**Критерий закрытия:** вызовы через HTTP и непосредственно через application одинаково отклоняют недопустимую сумму, до записи в БД; доменные тесты покрывают соответствующие ограничения.

### R3. P2 — интеграционные тесты используют схему из ORM, а не из миграции

**Где:** [tests/conftest.py](tests/conftest.py), строки 42–54; [compose.test.yaml](compose.test.yaml), строка 51.

**Как сейчас:** контейнер сначала успешно выполняет `alembic upgrade head`, но затем каждый интеграционный тест создает отдельную схему через `Base.metadata.create_all`. Поэтому приложение в этих тестах работает по таблицам из моделей, а не по только что примененной миграции.

**Почему придерутся:** изменение модели без правильной миграции может оставить функциональные тесты зелеными. Успешный запуск существующей миграции проверяет ее исполнимость, но не соответствие измененному приложению.

**Граница вывода:** текущая миграция не объявляется сломанной. `alembic check` заново прошел; предыдущие HTTP-проверки работали по мигрированной БД. Речь о неполном автоматическом барьере от будущей регрессии.

**Как исправить:** выполнять ключевые интеграционные сценарии в изолированной базе/схеме, подготовленной Alembic; добавить проверку миграций и их соответствия моделям в стандартную команду тестов. Явно проверять критичные ограничения и индексы. `alembic check` полезен, но наследует ограничения autogenerate и не заменяет проверку поведения схемы. [Документация Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html#running-alembic-check-to-test-for-new-upgrade-operations).

**Критерий закрытия:** удаление нужного ограничения/поля из миграции или добавление поля в модель без миграции ломает автоматическую проверку сдаваемого проекта.

### R4. P2 для внешнего размещения — нет политики допустимых адресов webhook

**Где:** [schemas.py](app/schemas.py), строка 29; [infrastructure/webhooks.py](app/infrastructure/webhooks.py), строки 35–57.

**Как сейчас:** проверяется форма HTTP(S) URL, но не разрешенность назначения. Адрес напрямую передается HTTP-клиенту. Отключение редиректов и proxy из окружения полезно, но не ограничивает сам адрес.

**Что воспроизведено:** адреса loopback и link-local проходят `PaymentCreate` и доходят до подставного транспорта `WebhookSender`. Настоящие запросы к внутренним службам или облачным metadata endpoint не выполнялись.

**Почему придерутся:** обладатель API-ключа может задавать назначения, доступные из сети consumer. Для внешнего сервиса это основание обсуждать SSRF — обращения к внутренним ресурсам по адресу, заданному клиентом. Наличие API-ключа уменьшает круг атакующих, но не задает список разрешенных назначений. Пользовательские webhook URL прямо упоминаются в [рекомендациях OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

**Граница вывода:** в локальном тестовом проекте обращение к `webhook-receiver` внутри Docker намеренное. Требование защиты внешнего размещения в ТЗ отдельно не сформулировано. Безусловно запрещать все частные адреса нельзя: это сломает предусмотренную демонстрацию.

**Как исправить:** определить явную политику назначения. Для демонстрации разрешать конкретный приемник, для внешнего окружения — согласованные адреса/сети и исходящие соединения. При проверке доменов учитывать все разрешенные IP и повторное разрешение DNS; не ограничиваться строковым поиском `localhost`. Проверять эту политику непосредственно перед отправкой. Выбор политики должен соответствовать реальному способу использования webhook.

**Критерий закрытия:** допустимый демонстрационный URL работает, запрещенные назначения отклоняются, а политика и ее пределы описаны.

### R5. P2/P3 — один важный сценарий сбоя проверен разово, но отсутствует в постоянном наборе

**Где:** [tests/integration/test_processor.py](tests/integration/test_processor.py); существующие проверки после строки 227 покрывают сбой сохранения результата шлюза и вставки retry. [test_outbox.py](tests/integration/test_outbox.py), строка 154, проверяет другой случай — подтверждение AMQP до commit outbox.

**Пробел:** отдельного постоянного теста «webhook уже получил 2xx, но сохранение `webhook_delivered_at` упало» в 127 тестах нет. Этот случай отличается от падения commit после publisher confirm и от обычного повторного вызова уже завершенной обработки.

**Что сделано в аудите:** после успешного подставного webhook внедрен сбой `before_commit`, затем та же команда обработана снова. Получено: два отправленных уведомления с одинаковым event ID, один вызов шлюза, успешная итоговая фиксация доставки.

**Вывод:** текущая реализация этот сценарий выдерживает. Это пробел регрессионного покрытия, а не найденная потеря платежа.

**Как исправить:** перенести диагностический сценарий в интеграционный тест: проверить неизменность результата и `processed_at`, одинаковый ID webhook, отсутствие второго вызова шлюза и прежний номер логической попытки. Дополнительно полезен отказ ACK после сохраненной доставки — повтор должен завершиться без нового внешнего эффекта.

### R6. P3 — документ в архиве не переносится вместе с проектом

**Где:** [AUDIT_COMPLIANCE.md](AUDIT_COMPLIANCE.md) и [scripts/package.py](scripts/package.py).

**Что подтверждено:** аудит, включенный в ZIP, содержит 11 ссылок на абсолютные пути `C:/Projects/Payments/...`. На компьютере проверяющего эти пути отсутствуют. В конце он также ссылается на `PROJECT_AUDIT_AND_LESSONS.md`, которого нет среди 66 файлов архива.

**Почему придерутся:** заявление «все проверено» трудно проверить по неработающим ссылкам. Кроме того, рядом находятся исторический отчет на 117 тестов и новый на 127. Исторический отчет явно помечен как старый, поэтому это не ложное число, но чтение усложняется.

**Как исправить:** использовать относительные ссылки внутри сдаваемых Markdown; включить нужный связанный документ либо сделать отчет самостоятельным без ссылки на отсутствующий файл. В README оставить однозначный путь к актуальным результатам и четко отделить исторические сведения.

**Критерий закрытия:** распаковать ZIP в другое имя каталога и пройти все ссылки документа. Проверка не должна зависеть от машины автора.

### R7. P3 — результаты пока не закреплены автоматической проверкой коммитов

**Что подтверждено:** конфигурации CI в проекте нет. Локальный pytest при отсутствии `TEST_DATABASE_URL`/`TEST_RABBITMQ_URL` намеренно пропускает соответствующие интеграционные проверки. Отдельный Compose обеспечивает полный прогон, но требует ручного запуска.

**Почему придерутся:** результат «127 passed» убедителен для этой рабочей копии, но не является автоматической гарантией для следующего коммита. Архитектурные тесты проверяют импорты четырех пакетов, а не все свойства архитектуры и не весь жизненный цикл worker.

**Граница вывода:** CI не был отдельным требованием ТЗ. Его отсутствие само по себе не делает задание невыполненным. Текущий полный Docker-прогон не имеет skips.

**Как исправить:** добавить одну понятную проверку на push/PR: lint, полный Docker-набор, миграции и контроль отсутствия неожиданных skips. Публиковать лог результата и версию исходников. Не наращивать формальные тесты ради количества.

## Отдельный риск сдачи: P1, если отправлять через GitHub

Последний локальный коммит остается `6ab5367 Initial commit`. Архитектурные изменения находятся в рабочей копии: измененные, удаленные и новые файлы не зафиксированы. Поэтому отправка только существующих коммитов не включит выполненный рефакторинг. Сам GitHub в этом аудите не проверялся; утверждение о содержимом удаленной ветки не делается.

Для сдачи через GitHub нужно проверить diff, включить новые каталоги и удаления в один осмысленный коммит, отправить его и убедиться, что в удаленной ветке присутствуют `domain`, `application`, `infrastructure` и актуальные тесты. Для сдачи ZIP существующий архив совпадает с проверенными исходниками, но замечание о ссылках в документации остается.

## Пять вопросов на защите, по которым решение можно объяснить

| Возможный вопрос | Что можно обоснованно ответить | Где проходит граница |
| --- | --- | --- |
| «Почему один consumer и общий `asyncio.Lock`?» | Один consumer прямо задан в ТЗ; очередь использует single active consumer и prefetch 1, локальный lock дополнительно сериализует вызовы одного processor. | Этот lock не является распределенной защитой. Нельзя обещать безопасность произвольного параллельного запуска processor вне выбранной топологии. |
| «Почему при публикации outbox открыта транзакция?» | Блокировка строки сохраняет владение событием до подтверждения брокера и commit; ожидание ограничено timeout. | Сетевое ожидание удерживает соединение. Для иной нагрузки возможен lease/claim, но это новый протокол с собственными рисками, а не обязательное исправление тестового. |
| «Почему webhook может физически отправиться больше трех раз?» | Три попытки — логический бюджет; авария между HTTP 2xx и commit допускает повтор того же события. Получатель дедуплицирует по стабильному ID. | Exactly-once не обещается. Разовый тест окна сбоя прошел; его стоит закрепить согласно R5. |
| «Почему DLQ заполняется явной публикацией, а не nack(requeue=false)?» | После исчерпания попыток событие DLQ атомарно сохраняется с состоянием платежа, затем публикуется с confirm. Это application-managed dead-lettering. | Топология сама не выполняет автоматический dead-letter через аргумент очереди; это не следует выдавать за реализованный механизм. |
| «Почему нет отдельного rollback-метода и богатой сущности Outbox?» | Контекст UoW гарантирует rollback при выходе без commit; это проверено. Outbox — техническая запись доставки, обычной структуры данных достаточно. | Отдельный метод не обязателен. Важно проверять фактическую транзакционную семантику и изоляцию ORM. |

Еще один вопрос — имена очередей внутри `application/events.py`. Там нет импортов RabbitMQ, но есть строки маршрутизации и формат сообщения. Для строгого подхода их можно преобразовывать в транспортном адаптере; в небольшом outbox-сервисе это защищаемый компромисс, а не возвращение SQL или бизнес-логики в consumer.

## Что не следует объявлять ошибкой без дополнительных требований

- `failed` от эмулятора — сохраненный бизнес-результат. Повторять само «списание» только потому, что webhook не доставлен, неверно; текущий код сохраняет результат.
- `pending` вместе с `exhausted_at` после технических ошибок шлюза не означает, что платеж успешно обработан. Это неопределенный бизнес-исход с исчерпанной обработкой; README объясняет разделение.
- Отсутствие CQRS, отдельного message bus, generic repository, сложной DI-библиотеки или десятка базовых классов не является дефектом само по себе.
- Подпись webhook, полноценные метрики, очистка старого outbox и административный redrive полезны для эксплуатации, но не были обязательными пунктами данного ТЗ. Их отсутствие нужно честно обозначать, а не автоматически расширять ими тестовое.

## Локальные доказательства и воспроизведение

Полный прогон и диагностические сценарии сохранены в `tmp/reviewer-audit-tests.log`, `tmp/reviewer-probes.log`, `tmp/reviewer-db-probes.log`. Временные скрипты `tmp/reviewer_probe.py` и `tmp/reviewer_db_probe.py` созданы только для аудита и не включены в пакет приложения.

Из корня проекта, при подготовленной Python-среде и запущенном Docker:

```powershell
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests tests
python -m tmp.reviewer_probe
Get-Content tmp/reviewer_db_probe.py -Raw | docker compose -f compose.test.yaml run --rm --no-deps -T tests python -
docker compose -f compose.test.yaml run --rm --no-deps -T tests alembic check
docker compose -f compose.test.yaml down
```

Первый диагностический скрипт использует подставной HTTP-транспорт. Второй требует `TEST_DATABASE_URL` тестового Compose и создает/удаляет только собственную схему. Проверки используют текущий код, не выполняют настоящих платежей и не отправляют сообщения компании.
