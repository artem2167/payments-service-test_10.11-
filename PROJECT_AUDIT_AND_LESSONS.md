## 1. Результат аудита и границы проверки

Основной недостаток проекта — слабое разделение бизнес-сценариев и инфраструктуры. SQLAlchemy-модели, запросы, транзакции, правила обработки и транспортные данные связаны напрямую. Функциональные проверки этого не устраняют.

Компания верно указала три особенности реализации:

- нет отдельного слоя операций хранения и собственной абстракции Unit of Work;
- нет независимой от ORM доменной модели;
- основной сценарий обработки находится в `messaging` и сам выполняет операции с БД.

При этом в проекте есть настоящие транзакции, выделенный класс `PaymentProcessor`, внедрение шлюза и отправителя webhook, интеграционные проверки PostgreSQL/RabbitMQ. Поэтому утверждения «транзакций нет», «вся логика написана прямо в callback брокера» или «проект вообще не разделен» были бы неточными.

## 2. Требования задания и критерии компании

### Что требовало ТЗ

API создания и чтения платежа, SQLAlchemy async/PostgreSQL, RabbitMQ/FastStream, outbox, идемпотентность, три попытки, DLQ, webhook, миграции, Docker Compose и README. Отдельно указана оценка архитектуры и чистоты кода.

Слова Repository, Unit of Work и требование независимых от ORM доменных сущностей в ТЗ отсутствуют. Поэтому отсутствие конкретного паттерна нельзя автоматически приравнивать к невыполнению функционального требования. Компания вправе оценить разделение ответственностей по общему архитектурному критерию; ее подробная внутренняя шкала из письма неизвестна.

Фраза «один обработчик, делающий всё» описывает обязанности consumer в сценарии. Она совместима с делегированием работы сервисам и репозиториям; помещать все обязанности в один модуль она не обязывает.

### Как понимать замечания компании

- Repository нужен для изоляции операций хранения, а не ради наличия папки `repositories`.
- Собственный UoW нужен как граница транзакционной работы приложения, а не как обязательная замена SQLAlchemy Session.
- Доменная модель нужна для выражения бизнес-правил независимо от БД. Отдельная копия всех полей ORM без поведения сама по себе эту цель не достигает.
- Сервисный слой нужен для организации сценария независимо от HTTP и RabbitMQ. Название каталога не подтверждает такую независимость.

Отсутствие каждого из этих элементов не является универсальной ошибкой для любого маленького CRUD-сервиса. В данном проекте сложность переходов состояния, повторной доставки и транзакционных гарантий делает их выделение обоснованным.

### Условия использования инструментов

В исходном ТЗ отдельно запрещено выполнение с использованием ИИ. Это условие участия в отборе, независимое от работоспособности и архитектуры. Для следующих заданий ограничения на инструменты нужно учитывать до начала работы. Если предполагаемый способ работы с ними несовместим, следует заранее согласовать допустимый формат или отказаться от такого задания. Переименование классов и переписывание стиля не решают вопрос соблюдения условий.

В приведенном письме компания объясняет отказ архитектурой. Считать именно использование ИИ установленной причиной этого конкретного письма оснований нет.

## 4. Подробный разбор архитектурных проблем

### A-01. Нет слоя операций хранения

**Где:** `app/services/payments.py:29`, `app/messaging/consumer.py:39`, `app/messaging/outbox.py:55`.

**Факт:** сервис создания собирает PostgreSQL INSERT и SELECT; processor читает ORM, использует `FOR UPDATE` и сохраняет изменения; relay строит выборку с `SKIP LOCKED`. `app/db.py` создает engine и sessionmaker, но не предоставляет бизнес-ориентированные операции хранения.

**Последствия:**

- изменения схемы и способов загрузки затрагивают несколько типов модулей;
- прикладной код должен знать ограничения SQLAlchemy и PostgreSQL;
- для проверки сценария приходится поднимать реальную БД или имитировать внутренности ORM;
- одинаковые правила выбора и блокировки записей могут начать расходиться.

**Как исправить:**

1. Определить небольшой контракт `PaymentRepository` под реальные операции проекта: атомарное создание при уникальном ключе, загрузка платежа, загрузка для изменения, сохранение перехода.
2. Определить `OutboxRepository`: добавить событие в текущую транзакцию, получить готовое событие для публикации, сохранить результат публикации/отсрочку.
3. Реализовать контракты через SQLAlchemy в инфраструктурном пакете. Выбор SQL, `ON CONFLICT`, `FOR UPDATE`, ограничения и `SKIP LOCKED` оставить внутри этой реализации.
4. Для GET разрешить отдельный read/query service, возвращающий read model. Не нужно загружать полноценный агрегат для каждого простого чтения.
5. Убрать `AsyncSession`, `select`, `insert`, `session.get` из прикладных сценариев.

**Критерий исправления:** прикладной сервис можно создать с in-memory реализацией репозиториев; он не конструирует SQL. Конкурентные гарантии отдельно проходят на PostgreSQL.

**Типичная ошибочная правка:** обернуть `session.execute(query)` в универсальный `BaseRepository.execute(query)` и продолжить собирать SQL в сервисе. Зависимость и ответственность останутся прежними.

### A-02. Транзакции есть, собственной границы UoW нет

**Где:** `app/services/payments.py:33`, `app/messaging/consumer.py:65`, `app/messaging/consumer.py:83`, `app/messaging/consumer.py:106`, `app/messaging/outbox.py:56`.

**Факт:** используются `session.begin()` и контекстные менеджеры. SQLAlchemy уже реализует отслеживание изменений по паттерну Unit of Work. Отсутствует прикладной контракт, который объединяет репозитории и задает единые правила завершения операции.

**Последствия:** транзакционные детали связаны с ORM; при добавлении репозиториев легко получить несколько независимых сессий или преждевременный commit в одном из них.

**Как исправить:**

- Ввести UoW, который на одну короткую операцию создает одну сессию и передает ее всем участвующим репозиториям.
- Выбрать один понятный способ завершения: например, явный `commit()` в сценарии, а при исключении или выходе без commit — rollback. Описать и проверить эту семантику.
- Создание платежа и первого outbox-события выполнять в одном UoW.
- Увеличение номера попытки и создание retry-события выполнять в одном UoW.
- Исчерпание и создание DLQ-события выполнять в одном UoW.
- Репозитории могут делать flush при необходимости, но не должны независимо завершать транзакцию.

**Критерий исправления:** ошибка вставки outbox откатывает платеж; ошибка вставки retry откатывает номер попытки; репозитории одного UoW используют одну транзакцию. Выход из незавершенного UoW не оставляет частичные изменения.

**Типичная ошибочная правка:** один огромный UoW на загрузку, ожидание шлюза, HTTP webhook и сохранение всего результата. Это меняет границы блокировок, удерживает соединение во время внешнего I/O и может нарушить требование «сохранить результат до webhook».

### A-03. Бизнес-сущность привязана к ORM

**Где:** `app/models.py:29`; переходы находятся в `app/messaging/consumer.py:71` и `app/messaging/consumer.py:105`.

**Факт:** `Payment` описывает таблицу и поля. Изменения `status`, `processed_at`, `current_attempt`, признаков доставки и исчерпания выполняются прямыми присваиваниями в processor. Независимой модели бизнес-правил нет.

**Последствия:** допустимые переходы трудно увидеть в одном месте. Новая точка входа может изменить статус или счетчик иначе. Проверка бизнес-правил опирается на ORM или интеграционный сценарий.

**Как исправить:**

1. Выделить независимую модель `Payment` и состояние обработки/доставки. Это может быть один агрегат с вложенным состоянием; добавление новых таблиц ради разделения классов не обязательно.
2. Перенести в модель или чистую политику проверки переходов: применение результата шлюза, повтор старого сообщения, отметку доставки, регистрацию ошибки и решение о следующей попытке/исчерпании.
3. Выразить состояния через enum и явные результаты операций. При уже сохраненном результате повтор уведомления не должен повторно менять бизнес-исход.
4. Передавать время и параметры retry явно, чтобы тесты не зависели от реального ожидания и глобальной конфигурации.
5. В адаптере хранения преобразовывать ORM в доменную модель и обратно либо применить ORM-маппинг независимого класса. Для этого проекта отдельный mapper проще объяснить и проверить.

**Примеры правил для самостоятельных тестов:**

- из `pending` можно сохранить один бизнес-результат;
- `failed` шлюза является завершенным бизнес-исходом и требует webhook;
- сбой webhook не превращает `succeeded` в `failed`;
- старое сообщение не увеличивает текущую попытку;
- после третьей неудачи новой рабочей попытки нет;
- доставленное или исчерпанное уведомление не запускается заново обычным дублем.

**Критерий исправления:** эти тесты выполняются без БД, RabbitMQ, HTTP, SQLAlchemy и FastAPI.

**Типичная ошибочная правка:** создать dataclass с теми же полями и оставить все присваивания и условия в processor. Копия данных появится, правила останутся распределенными.

### A-04. Прикладной сценарий размещен и реализован в messaging

**Где:** `app/messaging/consumer.py:21`; вызов из транспорта — `app/worker.py:98`.

**Факт:** класс `PaymentProcessor` уже отделен от RabbitMQ callback и получает шлюз/отправитель через зависимости. Но сам загружает ORM, проверяет исходное outbox-событие, управляет SQL-блокировками и меняет состояние. Это частичное, а не законченное разделение.

**Как исправить:**

- Создать прикладной `ProcessPayment` или `PaymentProcessingService` в пакете `application`.
- Сервис должен использовать UoW, репозитории, доменные правила, интерфейсы шлюза, отправителя и часов.
- Consumer должен разбирать и проверять транспортное сообщение, вызывать сценарий, затем применять политику ACK/quarantine/requeue.
- Прикладной сервис должен возвращать понятный исход либо типизированное исключение. Решение об ACK не должно прятаться в доменной сущности.
- Глобальную последовательность по ТЗ сохранить в worker/topology. `asyncio.Lock` сам по себе действует только внутри одного экземпляра процесса.
- Разделить технический сбой инфраструктуры, бизнес-отказ шлюза и неудачу доставки. Недоступность БД не должна расходовать логический бюджет повторов.

**Критерий исправления:** один сценарий можно вызвать из теста или другого адаптера без RabbitMQ; бизнес-правила при этом одинаковы. Consumer не выполняет SQL и не присваивает платежу статусы.

**Типичная ошибочная правка:** переместить прежний файл в `services` без изменения зависимостей. Это исправит размещение, но не смешение ответственностей.

### A-05. ORM передается через границы модулей

**Где:** `app/services/webhooks.py:5`, `app/events.py:7`, `app/api/payments.py:34`.

**Факт:** отправитель webhook принимает ORM Payment; фабрики событий создают ORM Outbox; API преобразует полученную ORM-модель в ответ. Сервис создания принимает Pydantic `PaymentCreate` из общего `schemas.py`.

**Последствия:** изменение таблицы затрагивает HTTP-интеграцию и сообщения. При появлении lazy-полей или изменении жизненного цикла сессии возможны дополнительные запросы и ошибки вне ожидаемой транзакции. `expire_on_commit=False` облегчает текущее чтение загруженных полей, но не создает независимой границы.

**Как исправить:**

- API преобразует HTTP-схему в прикладную команду; результат сценария — в HTTP-ответ.
- Webhook-адаптер принимает явный снимок уведомления: URL, стабильный event ID, бизнес-исход, сумма, валюта, metadata и даты.
- Доменное событие или прикладное описание события преобразуется в транспортный envelope и outbox-запись на соответствующей границе.
- Стабильный `event_id` должен сохраняться до первой отправки и повторно использоваться после рестарта. Нельзя генерировать новый ID при каждом построении payload.
- Разделить бизнес-результат платежа и техническую запись outbox. Outbox хранит доставку событий и не обязан становиться богатой доменной сущностью.

**Критерий исправления:** webhook-адаптер тестируется с обычными данными; домен не импортирует ORM, Pydantic-схемы API, RabbitMQ или HTTP-клиент. Общие enum и денежные правила не зависят от транспортного пакета.

### A-06. Проверено поведение, недостаточно проверены зависимости

**Где:** `tests/integration/test_processor.py`, `tests/conftest.py`, `tests/unit/`.

**Факт:** проверки обработки выполняются преимущественно через настоящую БД. Это полезно для транзакций, но не показывает возможность независимой проверки бизнес-сценария. Наличие каталога unit не означает, что правила платежа выделены в самостоятельный слой.

**Как исправить:**

1. Сохранить интеграционные тесты PostgreSQL и RabbitMQ.
2. Добавить unit-тесты доменных переходов и retry-политики.
3. Добавить тесты прикладного сервиса с небольшими fake-реализациями UoW, репозиториев, шлюза, отправителя и часов.
4. Проверять реализацию UoW/репозиториев контрактными и интеграционными тестами. In-memory fake не доказывает UNIQUE, блокировки или rollback PostgreSQL.
5. Добавить проверку зависимостей: domain не импортирует инфраструктуру, application не импортирует конкретный SQLAlchemy-адаптер, consumer не содержит SQL.

**Критерий исправления:** изменить RabbitMQ-адаптер можно без изменения доменных тестов. Ошибка ORM-маппинга ловится интеграционным тестом, ошибка бизнес-перехода — unit-тестом.

**Типичная ошибочная правка:** замокать цепочки `session.execute().scalar_one()` и объявить это независимым тестом бизнес-логики. Такой тест закрепляет устройство ORM-вызовов.

### A-07. Проверка готовности не разделяла разные виды качества

**Факт:** итоговая оценка была сосредоточена на выполнении ТЗ, краевых HTTP-ошибках и устойчивости к сбоям. Архитектурные компромиссы не были достаточно явно обозначены до сдачи. Формулировка «все ошибки исправлены» была слишком широкой.

**Как исправить процесс:** вести четыре независимых результата: соответствие требованиям, функциональная корректность, архитектурная пригодность и воспроизводимость комплекта сдачи. Для каждого фиксировать доказательства и ограничения.

**Критерий исправления:** в отчете можно одновременно написать «117 проверок поведения прошли» и «прикладной слой зависит от ORM; архитектурный критерий пока не закрыт». Никакой процент прохождения тестов не должен автоматически превращаться в «100% готовности».

Ниже предлагается структура для этого проекта. Перечисленные новые файлы еще не созданы; это карта рефакторинга, а не описание текущего дерева.

```text
    create_payment.py        # сценарий создания

  infrastructure/
    db/
      models.py              # ORM-таблицы payments/outbox
      mappers.py             # преобразования ORM/домен/read model
      repositories.py        # SQLAlchemy и PostgreSQL-запросы
      uow.py                 # сессия, commit/rollback, общий набор репозиториев
      queries.py             # SQL-реализация чтения
    messaging/

      outbox_relay.py        # публикация и ее транзакционные границы

    gateways.py              # эмулятор или внешний провайдер
    webhooks.py              # HTTP-адаптер отправки снимка
  api/

  main.py                    # создание HTTP-приложения

```

Правила зависимостей:

1. Domain использует стандартные типы и собственные правила; ничего не знает об API, ORM, AMQP и HTTP.
2. Application знает domain и контракты портов; не создает engine, session, RabbitBroker или AsyncClient.
3. Infrastructure реализует порты и может зависеть от domain/application.
4. API и consumer переводят внешний ввод в команду. Конкретные зависимости собираются в `main.py`/`worker.py` или отдельной точке сборки.
5. Возврат DTO и создание mapper не требуют дублирования каждой таблицы во всех слоях. Добавляется только нужная сценарию граница.

Для простого следующего CRUD-задания допустима более компактная структура. Выбор должен опираться на реальные правила и критерии задания; дерево выше не является обязательным шаблоном на все случаи.

## 7. Транзакции, конкуренция и окна сбоя

### Создание платежа

В одной короткой транзакции: атомарно создать платеж по уникальному ключу; при новом платеже добавить первое событие; при существующем сравнить нормализованный запрос; завершить commit или rollback. HTTP 202 означает сохранение намерения, а не завершение обработки.

Предварительный `SELECT`, затем `INSERT` без UNIQUE/обработки конфликта не обеспечивает идемпотентность. Репозиторий должен скрыть механизм разрешения гонки, а не убрать его. При использовании IntegrityError нельзя продолжать работать в сломанной транзакции без корректного rollback/savepoint; нынешний `ON CONFLICT` следует сохранить либо заменить доказанно эквивалентной реализацией.

### Обработка и webhook

Последовательность фаз для эмулятора:

1. Коротко прочитать и проверить платеж, номер попытки и идентичность исходного события.
2. При отсутствии бизнес-исхода вызвать шлюз вне долгой DB-транзакции.
3. В отдельном UoW повторно проверить актуальность состояния и сохранить исход с датой.
4. После commit отправить webhook по сохраненному результату и стабильному event ID.
5. В новом UoW сохранить доставку либо атомарно запланировать retry/исчерпание с соответствующим событием.

Повторная проверка состояния после внешнего ожидания обязательна: данные, прочитанные до него, могут устареть. Точная политика конкуренции должна оставаться совместимой с одним активным consumer по ТЗ.

В текущем контракте три логические попытки — общий сохраненный бюджет обработки: техническая ошибка шлюза и ошибка webhook могут расходовать его на разных этапах. Бизнес-исход `failed` сам по себе ошибкой доставки не является. Нельзя при разделении сервисов незаметно заменить общий бюджет на «три попытки шлюза плюс три попытки webhook». Для новой реализации нужна смешанная регрессия: технический сбой шлюза на первой попытке, сохранение результата и сбой webhook на второй, затем последнее допустимое выполнение на третьей.

### Публикация outbox

Текущий relay выбирает запись под `FOR UPDATE SKIP LOCKED`, выполняет ограниченную по времени публикацию и сохраняет ее результат в той же короткой транзакции. Это удерживает блокировку во время AMQP I/O; для текущего масштаба решение ограничено timeout и проверено на параллельных relay.

Нельзя просто перенести выборку в репозиторий, закрыть транзакцию, а затем публиковать: блокировка уже исчезнет, и второй relay сможет взять то же событие. Альтернатива с lease/claim требует сохраняемого владельца/срока, правил повторного захвата, миграции при необходимости и новых конкурентных тестов. Это отдельное изменение протокола, а не механический перенос файла.

### Таблица окон сбоя

| Момент аварии | Ожидаемое восстановление |
| --- | --- |
| До commit создания | Нет частично созданного платежа/события |
| После commit создания, до публикации | Relay позднее найдет outbox-запись |
| После confirm брокера, до commit отметки | Допускается повторная публикация того же события; обработчик должен распознать повтор |
| После сохранения исхода шлюза, до HTTP webhook | Повтор использует сохраненный исход и отправляет уведомление |
| После ответа webhook 2xx, до commit доставки | Допускается повтор с тем же event ID; получатель дедуплицирует |
| Во время сохранения retry-события | Попытка и событие откатываются вместе |
| При недоступной БД в обработчике | Незавершенное сообщение не ACK-ается; после восстановления возвращается в обработку |
| При испорченном сообщении | Quarantine/DLQ подтверждается брокером до ACK исходного сообщения |

Публикация сохраненных outbox-событий при последующем восстановлении инфраструктуры использует модель **at least once**. Webhook имеет ограниченный бюджет попыток: успешное получение произвольно недоступным клиентом не гарантируется, после исчерпания сохраняется событие для DLQ. Названия классов Repository/UoW не создают exactly once.

Если эмулятор заменяется настоящим шлюзом, появляется дополнительное окно: провайдер провел операцию, а результат еще не записан в БД. Для него нужны идемпотентность запроса у провайдера и/или сверка состояния. Текущая эмуляция и ее тесты не доказывают отсутствие повторного реального списания.

| Архитектурные границы | Нет запрещенных импортов и протекания ORM через типы | Статическая проверка + ревью | Добавить |

Дополнительно при изменении retry-политики тест должен выводиться из требования «три попытки», а не из текущего условия в коде. Проверка, которая специально ожидает четвертую попытку, закрепит дефект вместо защиты от него.

## 10. Процесс для следующих тестовых заданий

### До написания кода

1. Прочитать целиком ТЗ, условия участия, критерии оценки и ограничения инструментов.
2. Отдельно выписать функциональные требования, нефункциональные гарантии и требования к форме сдачи.
3. Для каждого требования определить наблюдаемый результат и способ проверки.
4. Выписать неоднозначности: три попытки всего или три повтора; какие ошибки повторяются; нужен ли строгий порядок; когда возможны дубли; что считается успешной доставкой.
5. Описать состояния и переходы до выбора каталогов и базовых классов.
6. При ожидаемой сложной бизнес-логике заранее определить границы хранения, транзакций и внешнего I/O. Если архитектурные ожидания команды существенно влияют на решение, уточнить их в начале.

Шаблон рабочей матрицы:

| Требование | Наблюдаемое поведение | Где реализуется | Как проверяется | Что остается неопределенным |

### Во время разработки

- Сначала провести один сценарий через выбранные границы: вход, команда, правила, транзакция, результат. Затем наращивать обработку ошибок.
- Для каждой внешней операции задать timeout, момент commit и поведение при повторе.
- Поддерживать таблицу окон сбоя. Слова outbox/idempotency/UoW должны соответствовать проверяемому механизму.
- Регулярно читать импорты и типы аргументов. Наличие ORM в сигнатуре HTTP-адаптера может быть важнее красивого дерева папок.
- Отделять повтор транспортного сообщения, повтор бизнес-сценария и повтор внешнего эффекта. Они не всегда совпадают.
- Применять реальные особенности требуемой БД/брокера в интеграционных тестах. SQLite и fake-брокер не доказывают блокировки PostgreSQL и маршрутизацию RabbitMQ.

### Перед сдачей

- Провести отдельное чтение архитектуры: кто принимает бизнес-решение, кто делает SQL, кто завершает транзакцию, кто подтверждает сообщение.
- Проверить негативные входы на уровне HTTP, включая формирование ответа об ошибке. Unit-теста валидатора недостаточно.
- Выполнить команды README в чистом окружении с явно заданными портами и переменными.
- Проверить число пропущенных интеграционных тестов. Успешный короткий прогон с skips нельзя выдавать за полный.
- Сверить документацию и комплект файлов с проверенной версией. Не включать `.env`, рабочее окружение, кеши и локальные журналы.
- Сохранять настоящую историю изменений по мере работы. Не создавать задним числом фиктивный процесс разработки или ложную атрибуцию.
- Уметь объяснить принятые ограничения и продемонстрировать небольшое изменение самостоятельно.

## 11. Косвенные признаки проблем и ошибочные исправления

### Пять менее заметных причин архитектурных замечаний

1. **Сигнатура выдает связь сильнее имени папки.** Функция в `services`, принимающая `AsyncSession` и возвращающая ORM Payment, остается связанной с хранилищем. Проверять нужно публичные типы и импорты.
2. **Смешаны разные виды состояния.** Бизнес-исход, доставка webhook и публикация сообщения имеют разные причины изменений. Общий «обработан» может случайно отключить недоставленное уведомление.
3. **Жизненный цикл ORM скрыт настройкой сессии.** Сейчас загруженные поля читаются после закрытия сессии благодаря особенностям использования и `expire_on_commit=False`. Это не гарантирует безопасную работу при появлении lazy-связей и не заменяет явный снимок данных.
4. **Количество тестов маскирует неверную точку проверки.** Проверка валидатора не проверяет сериализатор HTTP-ошибки; mock confirm не доказывает реальную маршрутизацию; интеграционный тест не доказывает независимость бизнес-правил.
5. **Обобщение меняет протокол незаметно.** Универсальный обработчик ошибок может начать тратить попытки на отказ БД; новый UoW может закрыть блокировку до публикации; второй worker может нарушить прежнюю последовательность. Эти изменения требуют специальных регрессий.

### Что не является исправлением

| Действие | Почему недостаточно |
| --- | --- |
| Добавить папки domain/repositories без изменения зависимостей | Сохраняется прежнее распределение обязанностей |
| Создать GenericRepository для каждого SQL-вызова | Прикладной слой продолжает знать детали хранения |
| Сделать dataclass-копию ORM без правил | Дополнительный mapper появляется, централизации инвариантов нет |
| Коммитить внутри каждого репозитория | Теряется атомарность платежа и outbox |
| Обернуть шлюз и webhook одной DB-транзакцией | Удлиняются блокировки; меняется порядок фиксации результата |
| Отметить outbox опубликованным перед confirm | Возвращается окно безвозвратной потери события |
| Заменить интеграционные тесты моками ради скорости | Исчезает проверка важных гарантий целевой инфраструктуры |
| Увеличить число тестов с теми же ожиданиями | Количество не компенсирует неверно выбранное требование |
| Объявить проект exactly once | Повтор внешнего эффекта остается возможен на границе HTTP/commit |
| Переписать документацию в уверенном тоне | Фактическое состояние реализации не меняется |
