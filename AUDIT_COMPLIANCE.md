# Аудит соответствия после рефакторинга платежного сервиса

## Текущие результаты после исправлений

В полном прогоне на PostgreSQL и RabbitMQ прошли **139 тестов без пропусков и предупреждений**. Ruff подтвердил форматирование 53 файлов. Отдельная проверка без подключения к тестовой БД показала, что обязательный полный режим завершается с ошибкой при пропуске интеграционного теста.

| Замечание | Что исправлено и проверено |
| --- | --- |
| Программные ошибки расходовались как повторы доставки | Шлюз, webhook и publisher сообщают об ожидаемых сбоях через явные типы ошибок. При неожиданной ошибке worker сохраняет бюджет попыток и журналирует тип исключения, идентификаторы и стек вызовов. Перед восстановлением он ждёт минимум 10 секунд. API возвращает `503` при потере соединения с БД и `500` при ошибке SQL. |
| Прямой вызов сервиса мог округлить сумму | Домен проверяет конечность, положительность, диапазон и целые копейки до вычисления хэша и записи. Интеграционный тест подтверждает, что `1.001` не создаёт ни платёж, ни outbox. |
| Тесты создавали схему из ORM | Тестовые схемы создаёт Alembic. На каждой схеме выполняется `alembic check`, после чего проверяются транзакции, ограничения и обработка сообщений. |
| Произвольное назначение webhook | API и worker сверяют схему, хост и порт с `WEBHOOK_ALLOWED_ORIGINS`. Проверены loopback, link-local, подмена хоста и порта, а также URL с логином. Compose допускает локальный демонстрационный приёмник. При внешнем размещении список должен содержать доверенные назначения с контролируемым DNS. |
| Нет регрессионной проверки сбоя после успешного webhook | После сбоя фиксации доставки повтор идёт с тем же ID и тем же номером попытки. Шлюз вызывается один раз. После успешной фиксации повторная команда webhook не отправляет. |
| Непереносимые ссылки и ручной запуск проверок | Ссылки в пакете сделаны относительными. [GitHub Actions](.github/workflows/checks.yml) настроен на тот же Compose-набор для push и pull request. Команда CI проверена локально. |

На отдельном демонстрационном стеке прошли авторизация, 20 параллельных идемпотентных запросов, конфликт ключа, доставка и исчерпание повторов. Проверены восстановление после остановки RabbitMQ и consumer, доставка после перезапуска PostgreSQL и сохранность результатов после перезапуска приложений. Запрос `/health` при остановленной БД вернул `503`.

## Исходный рефакторинг

Результаты ниже относятся к первому этапу от 9 ноября 2026 года. Исходная версия для сравнения имеет коммит `6ab5367fab3d21da0da800045b3cf3a81a9489d3`.

**Все три архитектурных замечания из письма закрыты по результатам проверки кода:** операции с БД вынесены в репозитории и Unit of Work, правила платежа живут отдельно от ORM, обработка выполняется в прикладном сервисе. Полный набор на настоящих PostgreSQL и RabbitMQ прошел: **127 тестов, без пропусков**. Оценка соответствует тексту замечаний; повторной оценки от компании не было.

## Что сделано по шагам

1. Зафиксированы прежний контракт HTTP и сообщений, три логические попытки, атомарность outbox и порядок фиксации результата. Исходный локальный набор: 75 тестов.
2. Выделены `Payment`, статусы и политика задержек. Состояние платежа и состояние его уведомления изменяются через доменные операции.
3. Введены контракты репозиториев, Unit of Work и внешних операций. SQLAlchemy-реализация отделена от сценариев. ORM-классы названы `PaymentRow` и `OutboxRow`, существующие таблицы и миграция сохранены.
4. Сценарии создания, обработки и публикации переведены на эти контракты. API формирует команду; RabbitMQ-обработчик преобразует сообщение в команду, вызывает сценарий и подтверждает доставку.
5. Webhook и RabbitMQ-публикатор переведены на простые структуры данных. Форматы внешних сообщений, стабильные идентификаторы и денежный формат сохранены.
6. Сохранены регрессии прежней версии. Добавлены 10 проверок, включая независимые правила и сценарий, транзакционный откат, границы импортов и повтор запроса с отпечатком, сохраненным старой версией.

В точках сборки `main.py` и `worker.py` импорты `SQLAlchemyError` используются для реакции на сбой инфраструктуры, а запросов там нет.

### Воспроизведение

В корне проекта с настроенным `.env` и запущенным Docker:

```powershell
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests tests
docker compose -f compose.test.yaml down
docker compose --profile demo up -d --build --wait
docker compose run --rm migrate alembic check
uv run --frozen python -m scripts.smoke --api http://localhost:18000
uv run --frozen python -m scripts.resilience --api http://localhost:18000
```

Подставьте порт из своего `.env`. Последняя команда временно останавливает сервисы демонстрационного проекта `async-payments`.

## Что важно сохранить в следующих изменениях

- Платеж и первое событие, а также номер повтора и его событие, сохраняются в одной транзакции. Commit остается на границе сценария, а не внутри репозитория.
- Вызовы шлюза и webhook выполняются вне DB-транзакции. Результат шлюза фиксируется до webhook. Relay удерживает блокировку только на время ограниченной публикации и записи результата; снятие блокировки раньше потребует отдельного протокола захвата.
- Outbox допускает повтор после подтверждения брокера и сбоя commit. Webhook тоже может повториться при сбое после HTTP 2xx; идентификатор события остается прежним. Это свойство доставки, а не гарантия exactly once.
- Сохраняется один активный consumer. Для реального шлюза потребуется отдельная идемпотентность у провайдера; здесь шлюз эмулируется.
